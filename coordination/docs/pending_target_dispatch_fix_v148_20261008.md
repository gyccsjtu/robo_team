# v1.48：待追踪目标的重派资格修复

## 问题与计划

v1.47修复远距原观察机优先级后，继续检查所有实际派机分支。发现_dispatch_pending_targets只检查connected和是否正在追踪其他目标，却没有首次_dispatch_tracker已有的_navigation_eligible和_navigation_task_allowed检查。结果：最近飞机即使仍处于导航阻塞冷却、或已经拒绝此目标任务，仍可能被重新标记为_tracking并收到意向；其他可用机无法被选中。这是源码和实际方法构造反例确认的缺陷，不声称它解释了WorkBuddy轮早期蓝色失败。

计划只补同一选机资格检查，不延长冷却、不删拒绝记录、不改变目标坐标或优先级；所有飞机不合格时目标保持待处理。冻结兼容v2.8，任务线上schema2保持。

## 已实现

待追踪目标选机与首次派机一样逐机调用_navigation_eligible及_navigation_task_allowed(uid,('target',tid))。不合格飞机不参与排序；全部不合格时不写_tracking、不登记observer、不发布任务。已有追踪机的位置刷新、旧目标唯一锁、STOP/停稳及保留占用规则不变。city配置增补pending_target_selection_revision用于区分执行快照。

## 检查

新增三项直接执行真实_dispatch_pending_targets的反例：导航冷却中的最近机应被跳过；特定目标任务被拒绝的最近机应被跳过；全员不合格时不产生任务/调度标记。旧代码三项均失败；修复后相关6项全通过，完整coordination/tests共852项通过。此检查不是实体效果证明。
