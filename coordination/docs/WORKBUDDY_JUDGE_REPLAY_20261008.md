## 0. 一句话结论

**0/6 的直接原因不是"发不出去"、也不是"间隔太长"，而是"坐标不够准"。**

裁判对每个目标维护一个 **15 秒**计时器，规则是（`score_cal.py:105-151`）：

```python
distance_sq = (msg.x - position.x)**2 + (msg.y - position.y)**2
continuous  = previous == 0.0 or now - previous <= DETECTION_INTERVAL   # 1.0 s
if distance_sq >= err_threshold**2 or not continuous:                  # 1.0 m
    _reset_detection(actor_id)        # ← 任一条不满足，15 s 计时全部归零
    continue
```

本轮我们**真的上报了 489 条**、裁判**真的收到了**（`judge.log` 里有 `find actor_5` × 25、
`find actor_0` × 5），但**每一条误差 ≥1 m 的消息都会把 15 秒计时清零重来**。
实测**最长连续段只有 3.1–5.7 秒**，离 15 秒还差 9–12 秒。

## 2. 方法：复刻裁判的状态机

`judge_sim.py` 把 `score_cal._process_actor_detection` 的判定**逐条复刻**，喂给它：
- 观察器自己收到的 `/actor_*_info` 消息（`kind='official'`）—— **就是裁判看到的那一份**；
- 观察器采样的 actor 真值（`kind='actor_truth'`，`[t, x, y, actor_id]`）。

**一处必须说明的方法要点**：真值采样约 **1 Hz**，而 walker 一秒走 **1–2 m**。若把消息匹配到
"最近的采样点"，会凭空引入最多 ~1 m 的误差 —— 恰好等于裁判阈值本身。**因此 `truth_at()` 使用
线性插值**。这一修正前后结论方向不变，但误差分布更可信（第一版用最近邻曾把 red1 的
`<1 m` 比例压到 48% 与 49% 之间波动）。

## 4. 结论：清零主因是"误差"，不是"间隔"

| | green | red1 |
|---|---|---|
| 清零总数 | 7 | 24 |
| **其中 `error_ge_1m`** | **7（100%）** | **23（96%）** |
| 其中 `gap_gt_1s` | 0 | **1** |

**⇒ 96–100% 的清零是"坐标误差 ≥1 m"造成的。** 间隔条件基本满足
（red1 的 365 条里只有 1 次超 1 s）。

**⇒ 要消除，必须在整个 15 秒窗口内保持"每一条"都 <1 m。** 以当前比例估算：
- green `<1 m` = 73% ⇒ 连续 15 s（约数十条）全部达标：`0.73^n` → **接近于零**
- red1 `<1 m` = 49% ⇒ 同样接近于零

**这解释了为什么"已经能连续上报几十秒"仍然 0/6**：**能连续 ≠ 每一步都对**。

## 5. 旁证与一处未解释的差异（诚实标注）

`score_cal` 只在**清零后首次通过**时打印 `find actor_N`，所以 `judge.log` 里的计数
可与模拟的清零次数交叉验证：

| 目标 | 模拟清零 | 理论 `find` 次数 | 实测 `find` | 判定 |
|---|---|---|---|---|
| **red1** | **24** | **25** | **25** | **精确吻合** ✅ |
| green | 7 | 8 | 5 | **差 3 次，未解释** ⚠️ |

**red1 的精确吻合**是一个强验证：独立复刻的状态机与裁判实际打印逐数一致，
说明"清零次数"这个量是可信的。

**green 的 3 次差异我没有解释清楚**，可能来自：
1. green 走的是 `_process_actor_detection`，而 red 走 `_process_red_detection` —— **两条路径的
   reset 逻辑不同**（后者在 invalid 时**不**调用 `_reset_detection`）；
2. 真值插值对 green 目标（`walk_0`，`animation_factor 5.1`）精度不足；
3. `position is None` 分支（真值缺失时也会 reset，我的模拟未覆盖）。

**这三点都属裁判侧代码语义，归 Codex 复核**。它**不影响 §3–§4 的主结论**，因为主结论
直接来自"消息误差分布 + 最长连续段"，不依赖状态机细节的可复刻性。

## 6. 与延迟分析的闭环（为什么"第一步：渲染/帧率"选对了）

上一轮已量化（`error_decomposition.py` / `latency_decomposition.py`）：

```
发布坐标 = 真值 − (滞后 × 目标速度) + 被限幅削掉的量 + 几何误差
滞后 ≈ 1.0 s = 图像延迟 0.786 s + 融合窗抹平 0.212 s
需要外推 1.997 m  vs  EXTRAP_MAX_D = 1.5 m  ⇒  95% 顶格、平均少补 0.50 m
```

本轮实测的 `<1 m` 比例（green 73% / red1 49%）与上述分解**方向、量级一致**。

**⇒ 完整因果链**：

```
渲染帧率只有配置的 25%（软渲染）
   → 图像延迟 0.79 s
   → 发布坐标滞后 1.0 s ⇒ 误差 ≥1 m 的比例 27–51%
   → 裁判任一条 ≥1 m 即清零 15 s 计时
   → 连续段 3.1–5.7 s < 15 s
   → 0/6
```

**这正是"相机帧率"被列为第一步的原因**：它是这条链的源头，且**动它一处，
`<1 m` 比例、连续段长度、准确性余量会同时改善**；而调 `EXTRAP_MAX_D` / 就绪阈值
只是把误差从一处挪到另一处。
