## 确认与纠正

1. **新版红色匹配方向正确，但接入断了。** 官方 `/actor_red1_info`、`/actor_red2_info` 均允许匹配两个红色真值，消息类别仍是 `red`，不要求参赛方知道官方人物身份。我们的 `yolo_target_bridge.py` 把两个内部槽都发布到 `/actor_red_info`；新裁判没有这个订阅。`adapt_red_judge` 遇到新版标记直接返回原源码，旧适配添加的统一红色订阅随之消失。应修参赛桥接的发布话题，保留内部几何槽与官方身份的区别，勿改官方匹配逻辑。
2. **新版人物行为改变，历史结果不能直接比较。** 新 `control_actor.py` 移除了瞬移；被上报、无人机水平距离不超过20米且三维速度大于1米/秒时触发2米/秒逃跑。1米/秒是触发条件，不是飞机比赛限速。规则 PDF 的30秒瞬移与新平台存在差异，不能宣称公开规则已更新。
3. **WorkBuddy 对逃跑输入缺失的诊断成立。** 其原运行没有启动官方 ground_truth/odom 发布源，旧位姿桥的速度又恒为0；零逃跑不能归因于飞机慢，也不能当作追逃成功。补输入应使用仿真世界无人机位置和实际速度，仅供官方人物环境，不给参赛控制读取人物真值。当前候选已有补线代码，尚需实体验证。
4. **两种 ActorInfo 不兼容。** 官方消息 MD5 为 `d57df6c0908e158da5273b4646f729dd`，仓库 robocup_swarm 版本为 `b19c42c4e8a205a44c00afb2c6f8754e`。仓库重复 `score_cal.py` 改用后者，不能视为无害的 import 替换。场景裁判及参赛桥实际均使用官方类型，因此不能泛化为当前全色上报均坏；应统一所有可能运行入口使用官方消息。
5. **新版红色计时仍有缺陷。** 直接执行原 `_process_red_detection`：只剩actor5、其计时已启动时，输入距真值100米的错误red坐标后，`count_flag[5]` 仍True，`find_time[5]` 不清零。原因是仅剩一个候选时拒绝计数最多1，重置却比较固定长度2。不能用这点凑消除结果；保留官方文件，另用独立准确度和时序证据核对15秒连续定位。

## 最短修复顺序

先修官方话题及消息类型兼容 → 确认六路人物环境里程计完整 → 离线验证对应接入边界 → 再用统一源码快照进行一轮六机验证。先解决接线错误，再讨论速度、注意力分配及绿白融合。不能以坐标抖动小代替误差小，也不能以旧轮零逃跑证明新平台追逃完成。
