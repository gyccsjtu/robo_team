# 部署检查清单

按顺序勾。**每一项都对应一个真实踩过的坑**，跳步会以"看起来正常但没分数"的形式出现。

---

## A. 环境就绪

- [ ] `roscore` / ROS Noetic 可用
  ```bash
  source /opt/ros/noetic/setup.bash && roscore &   # 能起来即可，然后 kill
  ```
- [ ] catkin 工作空间已编译，且其中有 actor 消息包
  ```bash
  source ~/catkin_ws/devel/setup.bash
  rospack find ros_actor_cmd_pose_plugin_msgs      # 必须输出路径
  ```
  > 缺这个包 → 感知节点 `import ActorInfo` 直接失败。
- [ ] XTDrone 就位
  ```bash
  ls $HOME/XTDrone/robocup/base.world               # 必须存在
  ```
- [ ] Python 依赖
  ```bash
  python3 -c "import cv2, numpy, ultralytics; print('ok')"
  ```
- [ ] 权重就位
  ```bash
  ls -l ~/catkin_ws/src/yolov11_ros/weights/best.pt
  ```
  > 必须是**双目版**（`robocup-yolo` 的 `best_yolo11n_bino_v1.pt`，5.2 MB）。
  > 旧的单目版类序是 `[green,blue,brown,white,red,red]`，与本节点的 `CLASSES` **不匹配**，
  > 混用会导致类别整体错位。
- [ ] 🔴 已给无人机装双目相机（**不做这步，后面全白搭**）
  ```bash
  python3 patch/add_stereo_camera.py --check
  ```
  > 期望 PX4 那份显示 `INSTALLED (2 sensor)`。
  > 显示 `BAD_INCLUDE` = 装成了官方的 multicamera 版本 —— **话题在、但没有帧**，
  > 跑一次不带 `--check` 的 patch 即可修好。详见 `patch/README.md`。
- [ ] 🔴 官方资产核对通过
  ```bash
  python3 scripts/verify_official_assets.py --gt ~/robocup_dataset_gt_v3/gt.json
  ```
  > 全 PASS 才说明"训练时的外观 == 比赛时的外观"。
  > 任一项 FAIL 都别急着往下走 —— 那意味着模型看到的和比赛看到的不是一回事。

## B. 启动全栈

- [ ] 一键启动
  ```bash
  bash scripts/restart_stack_fly.sh
  ```
- [ ] 看到 `STACK_FLY_OK`
  > 打印 `STACK_FLY_FAIL_WORLD` = 世界没起来（见 README §8.2）；
  > `STACK_FLY_FAIL` = MAVROS 没连上飞控（见 README §8.1）。
- [ ] 世界服务可用
  ```bash
  rosservice list | grep get_link_state
  ```
- [ ] 飞控已连接
  ```bash
  rostopic echo -n1 /typhoon_h480_0/mavros/state | grep connected   # connected: True
  ```
- [ ] 相机话题**有帧**（不是"话题在就行"）
  ```bash
  rostopic list | grep stereo_camera                          # 话题在
  rostopic hz /typhoon_h480_0/stereo_camera/left/image_raw    # 必须有帧率
  ```
  > 🔴 **只 `rostopic list` 不够**：装成官方 multicamera 版本时，话题会 advertise 出来，
  > 但 `hz` 永远 `no new messages` —— 很容易误判成"已经对了"。
  > 没话题 → `DISPLAY` 没设，Gazebo 相机不渲染（README §3.1）。
  > 话题在但没帧 → README §8.4 / `patch/add_stereo_camera.py`。
- [ ] 感知进程活着，且**没有**多余的 YOLO 节点
  ```bash
  pgrep -fc perception_real      # 应为 1
  pgrep -fc yolo_v11             # 必须为 0
  ```

## C. 接口正确

- [ ] 契约形状自检（不需要 ROS）
  ```bash
  python3 scripts/check_target_report_schema.py    # 退出码 0
  ```
- [ ] `target_report` 有数据在流动
  ```bash
  rostopic hz /coordination/target_report          # 约 PR_COORD_HZ（默认 2 Hz）
  ```
- [ ] 载荷形状**严格 5 字段**
  ```bash
  rostopic echo -n1 /coordination/target_report
  ```
  应形如：
  ```json
  {"target_id": "green", "frame_id": "world_enu", "xyz": [12.34, -5.67, 1.25],
   "confidence": 0.87, "observation_id": "obs-green-42"}
  ```
  > 多一个字段都会被核心拒；缺字段同理。**核心只会 logwarn，不会报错**。
- [ ] 裁判侧 6 条话题**都**有数据
  ```bash
  for t in green blue brown white red1 red2; do
    printf '%-6s ' $t; rostopic hz --window=20 /actor_${t}_info 2>/dev/null | grep -m1 average || echo "(无)"
  done
  ```
  > `red1` / `red2` 必须**各自**有数据。只有 `red1` 动 = 两个红色目标只宣布了一个，**少一个目标分**。
- [ ] 🔴 **`confidence` 语义已和核心负责人确认**
  > 核心 `core.py` 写死 `if d['confidence'] < 1.: return`，
  > 而本节点发的是 YOLO 原始置信度 ⇒ **坐标不会被核心采用**。
  > 这是当前最大的对接风险，见 README §6.3.1。**动手跑端到端之前必须先拍板**。

## D. 判据达标

官方判分是**两段式**（以官方 `score_cal_master.py` 为准，**不是**"必须连续 15 s 才有分"）：

- **+50 分「发现」= 单帧报对即可**（误差 <1 m、与上一帧间隔 ≤1 s），且中断后不回退；
- **+100 分「消除」= 自首次命中起连续 15 s 无中断**（间隔 <1 s，误差 <1 m）。

⇒ 50 分那档门槛极低；**6 个目标 × 100 的"消除分"才是真难点**。下面的检查按这个口径来。

- [ ] 发布间隔 < 1 s
  ```bash
  rostopic hz /actor_green_info      # 平均间隔必须明显小于 1 s
  ```
  > 主循环掉到 1 Hz 以下就危险了。最常见原因是**同时起了独立 YOLO 节点抢 CPU**。
- [ ] 目标进得了视野
  > 相机有效视野下缘约 −20°，悬停 5 m 时目标需 **> ~11 m** 才进画面。
- [ ] 目标落在 **12~15 m**
  > 定位误差：8–15 m 为 0.43~0.54 m；25–40 m 涨到 1.10~1.36 m。
  > 要过"误差 < 1 m"这条线，就得把目标压进 12~15 m。
- [ ] 连续达标时长实测 —— **这一步才决定有没有分，前面都只是前提**
  ```bash
  REC_OUT=/tmp/snap.jsonl REC_DUR=60 python3 scripts/rec_snap.py
  python3 scripts/judge_official_15s.py /tmp/snap.jsonl --target a3 --speed <实际速度>
  ```
  > 现状（2026-09-20 真飞实测）：**1 m/s 悬停观测，单机可以 PASS**（93.1% / 16.4 s）；
  > **2 m/s 单机必然 FAIL**（72.2% / 8.6 s，即便用真值速度补偿，天花板也只有 10.0 s）。
  > 目标往复穿越可见下边界会让时长打折 ⇒ **让目标稳定停在 12~15 m 是过线路径**。
  > ⚠️ 轮间方差大（同条件重跑可差 2~3 倍），写结论要用"N 轮里的最好/最差"。
- [ ] `PR_LAG_COMP` 是否真的有用（**别指望它**）
  > 快照里 `xyz` 是真正发出的值、`xyz_est` 是未补偿的滤波值，两者相减 = 实际补偿量。
  > 实测该量只有应有值的 **1/3** —— 因为**感知速度估计只有真值的 31%**。
  > 2 m/s 下 `=0` 与 `=0.35` 的单变量对照：单帧 64.5% → 65.6%，
  > 最长连续 4.1 s → 3.2 s（**反而退步**）。
  > ⇒ 开着无害，但**不要把它算进成绩预期**。要提升先修速度估计。

## E. 2 m/s 压测（官方逃逸速度已确定为 2 m/s）

> 官方规则写的是"被感知到后以 **2 m/s** 躲逃"，但官方 `control_actor.py` 目前仍是
> 恒定 1 m/s（**尚未更新**）。在官方改上去之前，先用开关把最坏情况跑一遍。

- [ ] 全程 2 m/s 跑一轮
  ```bash
  ACTOR_V=2 ./scripts/restart_stack_fly.sh
  ```
- [ ] 复现规则（平时 1 m/s，被追后 2 m/s）
  ```bash
  ACTOR_V=1 ACTOR_ESCAPE_V=2 ./scripts/restart_stack_fly.sh
  ```
- [ ] 用**固定几何**压测 —— 关键在"只改速度一个变量"（完整步骤见 README §10.5）
  > ① 先 `probe_actor_speed.py` 量真实速度，确认引导指令被精确执行（别信标称值）；
  > ② 把目标钉在 **14~15 m 视野正中**往复；
  > ③ 🔴 **必须杀掉该 actor 原来的随机游走控制器**（`control_actor_m2.py <id>`），
  >    否则它的 10 Hz 会盖过引导的 5 Hz：目标"看起来在动"，速度却完全不受控（已踩）。
  > ④ `kill` 与启动**拆成两条独立命令** —— `pgrep -f` 会和同一条 ssh 命令行里的启动串
  >    自匹配而自杀（已踩，废了一轮数据）。
- [ ] 出结论
  ```bash
  python3 scripts/judge_official_15s.py /tmp/snap.jsonl --target a3 --speed 2.0
  ```
  > 真飞实测（2026-09-20，目标 actor_3/white，60 s 仿真 ×4 轮）：
  >
  > | 速度 | 误差中位 | 单帧 <1m | 最长连续 | 官方 15 s |
  > |---|---|---|---|---|
  > | 1.0 m/s | 0.57 m | 93.1% | 16.4 s | ✅ PASS |
  > | 2.0 m/s | 0.70 m | 72.2% | 8.6 s | ❌ FAIL |
  > | 2.0 m/s + `PR_LAG_COMP=0.35` | 0.77 m | 65.6% | 3.2 s | ❌ FAIL |
  >
  > **单机在 2 m/s 下过不了 15 s 是结构性的**（真值速度天花板也只到 10.0 s）。
  > 出路只有两条：**悬停/慢速让目标不触发逃逸**，或**多机接力**（README §10.2）。

## F. 故障对照表

| 现象 | 最可能的原因 | 处置 |
|---|---|---|
| MAVROS 永远 `connected: False`，ARM 全被拒 | 世界里有残留无人机模型 → spawn 报 `entity already exists` → PX4 卡等 TCP 4560 | 重启 gzserver：`pkill -9 -x gzserver`，然后重跑 `restart_stack_fly.sh` |
| 世界起不来 / gzserver 段错误 | 完整 `base.world` 在本机内存下崩 | 用轻量世界 `launch/world_min.launch`；比赛前必须解决完整世界 |
| 无人机在，但没有图像话题 | `DISPLAY` 未设置，Gazebo 相机未渲染 | `source scripts/env_robocup.sh`（会自动起 Xvfb :95） |
| 核心收不到任何目标、不派任务 | ①字段集合不符 ②`confidence < 1.0` 被 `return` ③话题名不对 | 跑 §C 的两条自检；确认 §6.3.1 |
| 检得到但"连续 15 s"永远累不到 | 发布间隔 > 1 s（多为 YOLO 抢 CPU）；或目标掉出视野 | 确认没有独立 YOLO 节点；把目标维持在 12~15 m |
| 类别整体错乱 | 权重类序与 `CLASSES` 不一致（单目/双目混用） | 换回双目版权重，核对 `data.yaml` 类序 |
| actor 控制进程数 = 0 | `cwd` 不在 XTDrone 目录，或 `PYTHONPATH` 缺 XTDrone（`import ObstacleAvoid` 失败） | 用 `scripts/run_actors.sh`（已处理这两点） |
| 目标突然狂奔到地图边界卡死 | 逃逸三条件全中：UAV 水平速度 > 1 m/s **且** 距目标 < 20 m **且** 连续 > 20 帧 | 靠近时**慢速 / 悬停**（悬停不触发）；高速掠过会让目标跑掉甚至卡在边界 |
| 目标走得快时"连续 15 s"永远累不到 | 滞后误差 = 目标速度 × 链路延迟（实测 0.352 s 仿真；2 m/s 时横向项就有 0.69 m） | ① **慢速 / 悬停贴近**（悬停不触发逃逸）② **多机接力**（README §10.2）③ 别指望 `PR_LAG_COMP`：先修速度估计（当前只有真值 31%） |
| 压测时目标速度不受控（明明发了 v=2，实测却在慢慢走） | 该 actor 原来的随机游走控制器还在跑，10 Hz 盖过引导的 5 Hz | 先 `kill` 掉 `control_actor_m2.py <id>`；再用 `probe_actor_speed.py` 复量确认 |
| 起进程的 ssh 命令"提示成功"但进程不存在 | `pgrep -f` / `kill -f` 的模式与同一条命令里的启动串自匹配，杀掉了自己的 bash | **kill 与启动拆成两条独立 ssh 命令** |
| 目标速度被改成 2 m/s 了，怎么测 | 官方规则已定 2 m/s，代码尚未更新 | 见本清单 §E 的压测开关 |
