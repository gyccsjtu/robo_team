# 三维视线（LOS）判定改动说明

日期：2026-09-28
涉及文件：`src/core/swarm_task.py`、`src/core/swarm_agent.py`、新增 `src/core/swarm_heightfield.py`

---

## 1. 原来有什么问题

`LineOfSight.visible(ox, oy, tx, ty)` 是**纯二维**判定：从飞机到目标画一条水平射线，
途中碰到任意障碍栅格就判「看不见」。四个参数全是水平坐标，**没有 z**。

两个后果：

1. **飞行高度对可见性完全没有影响** —— 飞 4.5m 和飞 20m 判定结果一样。
2. **只看水平投影，不看实际高度** —— 一堵 2m 高的矮墙也会挡住 5.5m 高的飞机，
   尽管物理上视线明明从墙顶上方过去了。

雪上加霜的是，判定用的栅格是按 `robot_radius + safety_margin`（本项目 0.6m）
**向外膨胀过**的飞行安全栅格。膨胀区是空气不是墙，却会被当成实心障碍，
凭空多出一批误判。

## 2. 改成了什么

视线改成真正的空间线段 `(ox,oy,oz) → (tx,ty,tz)`：

```
沿线段按「半个格」步长采样，逐点比较
    z_ray(t) < 该处建筑顶面高度  →  判遮挡
```

于是「飞机比楼高」「离目标近、视线陡」都能自然判成可见。

### 高度数据从哪来

**没有改地图生成器。** `robocup_training_worlds` 输出的 metadata JSON 里，
每个障碍本来就带了 `z_max` / `height` 和真实 `footprint`
（38 栋楼是带 yaw 的 polygon，184 根灯柱是 radius=0.15m 的 circle）。
只是之前没人读——`GridMap.from_metadata()` 只取了二维占据栅格。

新增的 `swarm_heightfield.py` 把这些既有字段读出来、栅格化成高度场：

| 障碍类型 | 数量 | 高度 | footprint |
|---|---|---|---|
| building | 38 | 9.22 ~ 17.93 m | polygon（含 yaw） |
| lamp_post | 184 | 7.50 m | circle r=0.15 m |
| boundary_wall | 4 | 10.00 m | polygon |

**地图、actor、裁判系统均未改动。**

### 为什么不用 DDA 逐格步进

原二维判定用的 DDA 走 4-邻接格序列，斜射线在格角处会「切角」跳掉一格。
实测与逐点采样有 1.65% 分歧，且**总是偏乐观地判成可见**（漏判遮挡）。
半格步长采样不会漏格。三维分支改用采样，二维分支保持原样不动。

## 3. 向后兼容 / 如何回退

- `visible()` 的两个高度参数是可选的。不传、或构造时没给 `height_at`
  → 自动走原来的二维逻辑，行为与改动前**完全一致**。
- 起飞前 `local_z` 尚未就绪时同样自动走二维，不会误判成「看不见」。
- 想整机回退，不用改代码：
  ```bash
  export ROBOCUP_LOS_3D=0
  ```

## 5. 两条必须知道的结论

### 结论一：在 6m 限高内，飞多高都差不多

2m 到 6m 的可见率**一模一样**（80.3%）。原因很直接：这张图里最矮的障碍
是 7.5m 的灯柱，楼是 9.2~17.9m，**全都比允许飞行的高度高**
（裁判 `score_cal.py` 规定 z > 6.5 判 0 分）。

所以只要视线的水平投影穿过障碍，在合法高度内无论怎么飞都被挡。
**决定「看不看得见」的是水平位置，不是高度**——飞机得飞到目标的
「视线可达」位置上，而不是靠爬升。

这条也顺带说明：本次改动**不会**让检测率暴跌，反而因为修掉了膨胀区误判，
可见率从 69.9% 提到 80.3%（+10 个百分点）。

### 结论二：ORBIT_RADIUS=5.0 的参数注释可以放宽了

原注释写「收紧：离目标越近，2D 视线穿过建筑的概率越低」，
这是在补偿二维降维误差。三维判定下，距离 <5m 时可见率 97.4%，
<10m 时 92.7%。如果要更激进的搜索效率，这个半径可以适当放大重新扫参。

## 6. 待办 / 遗留

- `TARGET_KEYPOINT_Z = 1.25` 取自 Gazebo actor `init_pose` 的 z 值。
  若要更保守（按脚踝算）改 0.5，更宽松（按头顶算）改 1.7。
- 灯柱半径 0.15m 远小于栅格 0.5m，栅格化时按 `r + 半格` 处理保证至少落到 1 格。
  若觉得灯柱不该算遮挡，构造时传 `ignore_types=("lamp_post",)`。
- `docs/项目文档/问题.md` 里记的另一个降维问题（协同核心 `_build_offer()`
  用硬编码直角折线、`clearance` 恒为 25m）**未修**，是同类的下一处。
